# Forge deep-dive → what it tells caesar about typed workflow definitions

*Research artifact, 2026-08-01. Produced by a read-only survey agent over `/Users/sofo/Projects/forge/repos/forge` (Go 1.26 + CUE, 89 Go files ~9.3k LOC, 22 CUE files, single author, pre-1.0) and `/Users/sofo/Projects/forge/docs`. Empirical claims were verified by experiment, not inference.*

**Headline:** Forge is a working, well-organized Go+CUE meta-framework — and a natural experiment in exactly caesar's question. Its answer is uncomfortable: **CUE validates nothing at runtime in forge today.** The schemas are real, correct, and never called by the binary. The risk isn't picking the wrong schema language; it's building a type layer that sits off the execution path and decays into documentation.

## 1. What forge does end-to-end

Three tiers: **Forge (Tier 0)** = the grammar (CUE schemas + Go compiler + runtime + stdlib); **Archetype (Tier 1)** = a template repo for a *class* of platforms, composed from packages with open bindings; **Framework (Tier 2)** = one project with every binding resolved. The running system is deliberately *outside* the type system. Flow: scaffold → compose (git-fetched packages, flat, no lockfile) → author YAML instances (humans never write CUE) → `forge validate .` (seven check categories) → resolve (four-layer precedence merge, `forge why` provenance) → derive (filesystem facts, never hand-maintained) → execute skills (`run.sh` or `SKILL.md` via agent; pre/postconditions; SHA-256 provenance per generated file) → advisory upgrade/drift reports.

## 2. Where the CUE wiring breaks down (verified)

- **`schema.ValidateYAML` has zero callers.** Constructed, threaded into contexts, never invoked by any check. Injecting `maturity_state: TOTALLY_BOGUS_STATE` → `forge validate .` reports 7 PASS; `cue vet` on the same file correctly rejects it. The only real enforcement is `cue vet` shelled from the Taskfile against a hand-maintained glob→definition mapping (duplicated in a dead Go function that returns `nil` = valid on unknown names).
- **All ten concept types have zero Go structs** — everything is `map[string]any` with comma-ok access silently yielding zero values. Typed at rest, untyped in memory.
- **Live bug from the drift:** schema + all 22 skill files use `execution.modes: [script, agent]`; the Go code reads a scalar `mode` nobody defines — always `""`, so the run.sh/SKILL.md presence checks never fire. Deleting every `SKILL.md` and `run.sh` from all 23 skills still yields "skill PASS."
- Loading embedded CUE requires materializing a temp dir (CUE loader wants real paths); every validation round-trips YAML → JSON → CUE.
- **What CUE structurally cannot do here:** four-layer override precedence (unification is commutative; "higher tier replaces value" is hand-rolled in Go; CUE only validates the result). Any layering/overlay design needs the same split.
- Forge's own spec 006 exists because spec and implementation drifted ("20 items: 6 breaking, 7 significant"); the structural cause still ships.

## 3. Package maturity

`runtime` (drift/deferral/upgrade/three-way merge) and `scaffold` are genuinely good and well-tested. `cli` mature, thinly tested. `validate` mature in structure; skill checks dead. `skill` half-stub (`RunAgent` honestly errors "requires manual execution"). `policy` — **OPA/Rego discovery + evaluation of deny/warn rules over the resolved graph — working, and notably never specified, only built; the most caesar-ready code in the repo.** `graph` is **not a graph** — a map plus indexes, no edges, no cycle detection. `schema` — dead code. `gitops` works; no lockfile, floating semver. `#AgentProfile` exists in CUE (capabilities, `human_review: none|recommended|required`, `parallelizable`, `depends_on_output`) with the comment "Forge declares capabilities; orchestrators decide routing" — consumed by zero Go code; a sketch of caesar's problem left as an artifact.

## 4. The docs corpus

- **forge-spec v1 → v1.1:** nine changes, all from peer review. Dual-mode skills (`skill.yaml` + `SKILL.md` + optional `run.sh`; compiler never parses Markdown); `<scope>/<id>` namespacing; **declared vs derived state** ("codebase is source of truth for structure; manifest only stores what can't be inferred"); advisory-only upgrades ("generator-not-governor"); flat package deps. v1.1 quietly *deleted* v1's claim that CUE is "more expressive than JSON Schema." Go structs never considered as an alternative. §7.4 has the one table to read: explicit code-vs-AI boundary (schema validation / dependency resolution / template expansion = deterministic Go; convention interpretation / domain design / adaptation = AI).
- **meta-ontology v1 → v2:** v2 opens by criticizing v1's conflations; organizing insight is **change rate** (spec slow, compiler medium, stdlib fast → separate repos); composition replaces inheritance ("an archetype is NOT a child of another archetype"). Zero occurrences of "deterministic," "idempotent," or "CUE" in either.
- **Production-Grade Platform Mindmap v1 → v2:** Inner Ring (CI gates that block) vs Outer Ring (practices audited on cadence); v2 adds a Regulatory Ring + Cost/FinOps and Data Architecture & Governance pillars — the latter maps ~1:1 onto an orchestrator's core (lineage, retention per data type, schema validation at ingestion, data contracts).
- **Gap analysis:** ~82% vs 14 frameworks; "gaps are strategic, not foundational."
- **"Intentionally Deferred Frameworks and Practices"** — the most reusable doc; its *template* matters: each deferral = what it is → why deferred → **activation trigger** → near-zero-cost do-now → implementation outline → effort, plus a quarterly review table. Heuristics: "80% of the value at 10% of the cost"; "the gap is not in practice but in evidence collection."
- Aside: `docs/archive/` contains a code-review PDF of a Go/Postgres/NATS deposit pipeline that reads as a ready-made correctness checklist for a durable step executor (always-ACK message loss, missing status-regression guards, idempotency without `FOR UPDATE`, missing unique constraints, float money).

## 5. Verdict for caesar

**(a) CUE?** The honest case for: better than JSON Schema at defaults/composition/discriminated unions; native Go SDK; users author YAML/JSON. The case against, from evidence: forge paid for CUE twice (schema + Go consumption of the same data) and got zero in-memory type safety and a shipping drift bug; validation lived off the execution path and enforced nothing. **Recommendation: don't start with CUE. Go types as the single source of truth; validation as ordinary Go code on the write path (the API that persists a definition is the only door in); generate JSON Schema from the Go types for editors/UI forms.** Revisit CUE only for layered org-policy overlays — and even then the merge is Go; CUE only validates the result.

Two non-negotiables regardless of format: **validation on the write path, not a separate command** (a forgettable `caesar validate` is documentation), and **content-address the definition** (hash the fully-resolved, defaults-applied definition; store the hash on every run — forge's floating semver + wall-clock stamps made resolution repeatable in principle, not replayable in practice).

**(b) What transfers:**
- **The skill contract, nearly verbatim** — the single best thing here: `type` (generative/operational/verification) + typed `inputs` + `preconditions` + `postconditions` + `verification` + **declared effect set** (`affects_*`). A Hoare triple plus effects = exactly what a caesar step needs; declared effects enable safe parallelism and impact analysis.
- **Dual-mode execution** (`run.sh` deterministic, `SKILL.md` agentic, `auto` picks) — mechanical work in code, adaptive work in the model, declared per step.
- **Declared vs derived state** — authored definitions and computed run state in different stores; humans never hand-edit the derived side.
- **Policy as OPA-shaped deny/warn rules over a resolved projection** — gates, tool allowlists, approval requirements fit directly.
- **Decision as a first-class typed record**; **Deferral with a trigger and review schedule** (a paused branch that reactivates on a condition — good model for approval gates).
- **Provenance with per-artifact SHA-256** and advisory three-way diffs.
- **`#AgentProfile`'s fields** as step metadata: `human_review`, `parallelizable`, `depends_on_output`, capabilities.

**(c) What to avoid:**
- The maturity vocabulary (Pillar/Dimension/Practice/`absent→…→verified` describes disciplines over quarters, not executions over seconds).
- Entities nothing reads (`#Relationship`'s 15 verbs never instantiated; `#Artifact`/`#Dimension`/`#Evidence` consumed by no check) — schema tax.
- Calling it a graph without edges — for a workflow DAG, missing cycle detection is a correctness hole.
- Schema/runtime type divergence — the `execution.modes` bug is the single most transferable warning.
- Stubs that report success — `RunAgent` erroring honestly is fine; a validator silently passing on a field-name mismatch hid its failure for the project's whole life.
- The structural mismatch: forge models only the static; **nothing in this corpus addresses retries, timeouts, concurrency, partial failure, compensation, or replay.** Copy the type discipline and skill contract; don't expect the ontology to carry the hard part.
