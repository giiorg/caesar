*Research artifact, 2026-08-01. Produced by a read-only survey agent over `/Users/sofo/Projects/bitnet/ai-augmented` (the only *running* predecessor: 1,061 LOC, one Temporal workflow, five activities) and the vision corpora at `/Users/sofo/Projects/bitnet/ai-augmented-development-platform` (+v2, + peer review) and `/Users/sofo/Projects/bitnet/ai-augmented-v2/docs/foundation`.*

## A) The Temporal implementation

**Workflow/activity split is textbook and worth copying as discipline.** The workflow file contains nothing but `ExecuteActivity` calls — no clocks, randomness, or I/O; every side effect lives on an `Activities` struct. Determinism respected by construction. **Cleanup via disconnected context is the best pattern here:** both `Cleanup` and `PostErrorNote` run under `workflow.NewDisconnectedContext`, so temp clones are removed and the developer gets a failure comment even when the workflow context is cancelled — caesar needs exactly this for worktree teardown. Retries are tiered per activity class (clone 2min/3×; review 30min/2×; API posts 60s/4×). **Idempotency done right and better than the design doc:** workflow ID = `mr-review-{projectID}-{mrIID}` with `REJECT_DUPLICATE` (the doc had proposed a timestamp suffix, which would have defeated dedup entirely); cost — `REJECT_DUPLICATE` also blocks legitimate re-review (caesar: prefer `ALLOW_DUPLICATE_FAILED_ONLY` semantics).

**Two live defects worth carrying as negative examples:**
- **The heartbeat is never sent.** `HeartbeatTimeout: 5m` is set; `activity.RecordHeartbeat` is never called; any real review >5min is killed as heartbeat-timeout, retried, killed again. The plan doc specified the heartbeat explicitly; never implemented. Clearest argument for caesar owning its own agent-execution loop rather than treating a 30-minute LLM run as an opaque activity.
- **The gateway swallows every error as HTTP 200** ("check if it's an already-started error" — the check was never written): a Temporal outage and a duplicate webhook are indistinguishable to the caller.

**How `claude -p` is actually wrapped:** `claude -p <prompt> --output-format json --json-schema <schema> --max-turns <n> [--max-budget-usd %.2f]`, `cmd.Dir = repoDir` (deliberate: loads target repo's CLAUDE.md). **The advertised sandbox does not exist:** `--allowed-tools` never passed despite plan + CLAUDE.md claiming it in three places; no `--permission-mode`, no `--no-session-persistence`; `cmd.Env` never set → child inherits everything including `GITLAB_TOKEN`. Blast radius contained by luck (throwaway clone), not design. Output parsing: envelope unmarshal, require `structured_output`; **`is_error` parsed and never checked** — an internally-failed run emitting schema-valid JSON records as success. No exit-code classification; no runner-level timeout; stdout buffered wholesale (killed run → nothing at all).

**Layer model (six boxes):** Process backbone (GitLab CI + Jira + Slack, "source of truth", compliance-justified) · Governance = **Forge** (Go CLI, no daemon: `status/drift/next/diagnose` over `.forge/manifest.yaml` evidence probes — **the design trick worth stealing: it emits only exit codes and JSON; CI decides whether to block; "removing Forge does not break any workflow." The flaw: no severity, no owner, no waiver mechanism → bypassed the first time it blocks a hotfix**) · Temporal orchestration · n8n (justified by *audience*, not capability) · Agent Gateway (~150 LOC translation seam; **no authentication described at all**) · Capability layer (Claude Code plugins; "the same SKILL.md works in both contexts because it describes *what*, not *how* invoked") · Agent layer (human-supervised, or autonomous `claude -p` with `--permission-mode bypassPermissions` in sandboxed CI). Everything HTTP/REST; no shared DB, no broker between layers. Jira coupling total and unabstracted (ticket keys in branch names, workflow IDs, sprint identity) — caesar needs a work-item abstraction from day one.

**Tested: nothing.** Zero test files, no CI, manual four-terminal verification procedure — while `go.temporal.io/sdk/testsuite` makes replay tests nearly free and the corpus's own peer review names an evaluation harness as priority #1.

## B) The vision corpora

**Four generations, two disjoint systems sharing a vocabulary.** The v1/v2/Implementation-Guide lineage is a *repo-and-CI governance model for humans using Claude Code interactively* (six repos, YAML frontmatter specs, CI gates, no runtime). The v3/v3.1 lineage is a *distributed runtime for autonomous agents* (Temporal, NATS, K8s Jobs, pgvector). They never reference each other — **the seam between them is itself an unbuilt requirement, and it is arguably caesar's actual product.**

Governance lineage: seven personas, five lifecycle phases, "Two Loops" (fast sprint loop, slow discovery loop on spec-declared metrics). Two carrying principles: **"Deterministic where possible. If a rule can be expressed as code, it must be"** (caesar's thesis, stated years early) and **"Context is infrastructure"** (prompts/configs versioned, reviewed, owned like production systems). Scope boundary: "not a headcount reduction tool; a waste reduction tool." Runtime lineage thesis: "the production, distributed equivalent of Claude Code's native Agent Teams — every process-local primitive replaced by a networked, isolated, observable counterpart" (with a literal 20-row translation table). Domain context: regulated fintech; sensitive flows named and gate-worthy (auth, KYC, limits, fund movements, regulatory reporting).

**Governance/roles/approval — the transferable designs:**
- **Best idea in the corpus: approval routing derived from artifact metadata.** A spec's `dependencies:` frontmatter *is* the policy — `design: required` → designer becomes required reviewer; `security: required` → security sign-off mandatory. "No manual assignment needed." Generalize: **policy as a projection of declared work attributes.**
- **Second-best: agent permission as a derived projection of human permission** — "AI agent sessions inherit human repo access… enforced structurally, not by prompt instructions."
- Human write matrix is **path-scoped within repos** (Designer: `design/` + frontend tokens; PM: epics/stories + domain docs), read universal, plus a distinct **comment-only** tier → caesar's minimum ladder: read / comment / path-scoped-write / approve / admin.
- **v3.1 HITL policy engine:** L1 YAML baseline in Git (Git is the change-control mechanism) → L2 per-run override ("human-initiated, logged, never automated; applies to ONE run — next run reverts") → L3 adaptive ("auto-tightens, never auto-loosens"). Three gates (`plan_approval`, `mid_task_ambiguity` on confidence < 0.55, `pr_review`), each with conditions, timeout, and explicit `timeout_action`. Evaluation yields an **immutable policy struct** for the run. Kill switch: failure rate > 0.80 over 5 runs suspends a category until a human edits YAML.
- Repeated three times, load-bearing: **"AI-generated code is reviewed identically to human-written code. No fast-track merge path."** No auto-merge anywhere in any generation.
- **Missing across all four generations (caesar's greenfield):** multi-tenancy, user accounts, agent identity. One shared `@bitnet-agent` service account — **the decision most worth reversing**: a single bot identity means the forge audit log answers "what" but never "on whose behalf." Also absent: authorization on *who may start a workflow*; any policy-as-code engine; any approval UI (every gate terminates in a Slack button, and the decisions doc concedes "Slack notifications get ignored").

**Unrealized ambitions → candidate caesar requirements (ranked):**
1. **The evaluation harness** — "build it first; everything else follows from being able to measure." Offline golden set gating merges on prompt/template changes + weekly online sampling; baseline as a one-way ratchet. Written three times, never built.
2. **Replay** — "your team will abandon the platform the first time it creates a phantom bug." `agent-debug --task-id X`: snapshot, pinned runner image + git SHA, full conversation history, step-through with no broker dependency and no push. Rule worth stealing verbatim: **the debug path must never depend on an observability tool** (history from Postgres, not Langfuse).
3. **Idempotency at every boundary** — retracted "exactly-once" → concrete mechanics: signal IDs `{task_id}:{signal}:{attempt}:{seq}` as producer dedup + consumer processed-set; `next_seq` persisted in checkpoint state *before* publishing; transactional outbox for terminal signals; webhook idempotency keys from provider delivery GUIDs.
4. **Cost governance** — tracked everywhere, enforced nowhere (Grafana panel, no hard kill). Observed: $18.50/overnight sprint, $34.20/full day, 14min avg/ticket.
5. Others: the L2 override UI (caesar's React UI *is* this); metrics schema that resolves (`source`/`dashboard_url`/`metric_name`/`owner`); machine-checked traceability with **warn→block escalation**; spec amendment path for mid-run invalidation; agent-to-agent peer review (one MCP line implying an unbuilt reviewer role); multi-executor routing (interface specified, one backend); build-image matrix ("one runner image cannot rule them all without becoming a 10GB monolith"); outcome metrics — cycle time, rework rate, escaped defects, first-deploy E2E pass — with the anti-pattern named: "don't track lines generated, suggestions accepted, or AI usage frequency."

## Inherit / drop for caesar

**Inherit:** (1) the runner inversion — AI as subroutine, Go validates every proposed path/command before applying — "best decision in the stack"; (2) determinism = "Go performs the side effect, the LLM only proposes it" — and caesar must state publicly which determinism it claims (control-flow determinism + pinned definitions, not bit-identical LLM replay); (3) natural-key run IDs with explicit reuse policy (allow-after-failure); (4) metadata-derived approval routing; (5) agent authority as projection of requester authority; (6) the three-layer policy engine with its asymmetry + kill switch; (7) disconnected-context cleanup; (8) mirror-clone + per-run worktree ("git.lock conflicts structurally impossible"); (9) failure classification before retry + novelty detection (hash stderr+stdout; repeat hash → escalate; security failures get zero retries and leave the worktree for inspection); (10) two clocks (execution budget pauses during human waits; wall clock never); (11) the Forge trick — governance emits data, not verdicts; add severity/owner/waiver-with-expiry; (12) replay as a Phase-1 feature.

**Drop:** (13) Temporal — but keep the bridge *principle* (durable-execution engine behind a translation seam) and Temporal's *discipline* (workflow/activity determinism boundary) as caesar's own orchestrator invariant, since that discipline is what makes replay possible; the corpus's own verdict: "you cannot skip V1… build [the distributed tier] only when V2 falls over." (14) GitLab specificity, Jira coupling, Slack-as-UI — design the forge port around a `ReviewComment{path, line, side, body}` primitive with per-forge adapters and plain-comment fallback; work-item abstraction from day one; caesar's React UI as the primary approval surface with an auditable queue, delegation, expiry. (15) The whole infrastructure tier as *requirements* (EKS/Karpenter/EFS/n8n/Redis; NATS doing four unrelated jobs is a coordination-path SPOF) — noting caesar *does* deploy on an existing k8s cluster, which changes the substrate, not the software architecture. Also noted: a 28-category OSS tooling scan recommended "buy" for 27 — and **could not name a single tool for orchestrating agentic coding workflows; the category isn't in the map.** (16) The single shared service account and `bypassPermissions`-as-security-model — carry a requester principal end-to-end, per-run scoped credentials, record the initiating human in commits/PRs, and actually pass the tool allowlist the predecessors only promised.
