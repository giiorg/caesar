# caesar — subscription-first personal-mode auth (V1 amendment)

**Date:** 2026-08-05 · **Status:** all 6 sections approved by the user in the brainstorming session of 2026-08-05; codex artifact-review rounds 1–2 applied 2026-08-05 (round 1: 3 Blockers, 1 Major, 1 Minor — delayed-retry contract, open-CONNECT pairing, lease/sync-back protocol, honest exposure boundary, size cap; round 2: 1 Blocker, 3 Majors — accepted loss window replaces the zero-loss claim, chargeable-failure counter pinned, lease fencing + idempotent sync receipt, redaction narrowed to sensitive fields with quarantined-log rescan; round 3: 1 Blocker, 3 Majors — terminalization-never-skips-sync-back ordering, zero-charge contention + `credential_busy`, epoch fence distinguishing worker from reconciler, scan on decoded canonical patch bytes; round 4: 2 Blockers, 2 Majors, 1 Minor — mutable-credential aggregate moved wholly into assets (context-boundary law), cleanup fence on the auth directory, import-as-exclusive-custody-transfer + fingerprint dedup, immutable credential binding through the runner contract, pinned rate-limit fallback scheduling); awaiting user review of this document. · **Amends:** `2026-08-02-caesar-v1-design.md` §3 (execution & isolation — provider-credential custody) and the Plan 09 metering scope; everything else in the V1 spec stands. · **Consumed by:** Plan 07 (harness drivers), which this spec reshapes to subscription-first.

caesar V1 is a **personal, single-user, self-hosted platform**: one operator (the admin) running caesar on hardware they control — a MacBook first, possibly a dedicated Hetzner box later. The agents it orchestrates (Claude Code, Codex CLI) authenticate with the **operator's own consumer subscriptions** (Claude Max, ChatGPT) — the same way the operator uses those CLIs interactively today, with caesar as a thin orchestration layer on top. The operator is physically in the loop and re-authenticates when a login expires. No ToS workarounds: one individual, their own subscriptions, their own tasks.

---

## 1. Scope & posture

- **Subscription auth is the primary, day-one path.** API-key auth (`model_key`) remains a supported credential kind, but Plan 07's harness drivers are designed and verified subscription-first.
- **Multi-tenant / caesar-as-a-service is explicitly out of scope.** Anything that only matters when serving *other people's* credentials — gateway-side OAuth refresh, brokered provider custody as a hard requirement, per-tenant metering — is deliberately not built. This is a posture decision, not a temporary gap.
- **This amendment touches auth and its direct consequences only.** The workflow model and forge-credential handling are unchanged. The Plan 05 spine gains exactly one extension (the delayed-retry contract, §4); the Plan 06 runner gains the auth-directory mount, redaction scan, and open-CONNECT pairing (§3) — all owned by Plan 07.

## 2. Credential model

Two new credential kinds join the existing encrypted store (`forge_token`, `model_key` — Plan 03 envelope encryption and use-auditing unchanged):

- **`subscription_token`** (Claude Code): a static string, ~1-year lifetime, minted by the operator via `claude setup-token` on any machine (the flow prints the token to the terminal; it is not saved anywhere by the CLI) and pasted into caesar. No refresh machinery — when it dies, the operator mints a new one.
- **`agent_auth_file`** (Codex): a *mutable file* (`auth.json`) containing tokens the CLI refreshes itself. Provided by the operator via `codex login --device-auth` on the caesar box, or by logging in on a laptop and copying `~/.codex/auth.json`. caesar validates it is well-formed JSON and reads only pinned paths from it — the sensitive token fields for redaction (§3) and the refresh-token fingerprint (below) — never modifying it or depending on the rest of its schema.

**Sync-back & single-flight protocol (`agent_auth_file` only).** OAuth refresh tokens may rotate on use, which creates two hazards: a rotated-then-lost file strands the credential (the CLI invalidated the old refresh token and the new one died with the container), and two concurrent runs refreshing independently can invalidate each other. Naive "read the file back after exit" handles neither — a worker crash mid-run, a reconciliation kill, or an operator re-pasting the credential mid-attempt all corrupt it. One durable protocol covers both hazards, with all state in Postgres per the sole-authority rule:

1. **Credential lease, fenced by epoch, owned by one context.** The entire mutable-credential aggregate — ciphertext, `secret_version`, the lease with its takeover epoch, and sync receipts — lives in the **assets** context, because the sync-back commit must be atomic across all of them and transactions never span bounded contexts (V1 arch law, mechanically enforced). assets exposes acquire / heartbeat / takeover / sync-commit / release command ports; runs consumes them the way it consumes `UseCredential` today. The lease *is* the single-flight mechanism (an in-memory mutex would not survive restarts or multiple processes). It carries a **takeover epoch**, not just the owning phase-run id — because after heartbeat expiry the original worker and its reconciler are the *same* phase run, and identity alone cannot fence one from the other: reconciliation atomically advances the epoch *before* killing or reading the container, and a sync-back commit is valid only under the current epoch, so a paused old worker can never commit a stale snapshot after takeover. **A heartbeat-expired lease is not acquirable by a new attempt until the owning attempt's reconciliation — including its guarded sync-back — has concluded**; expiry alone never breaks single-flight, because the old container may still be alive and refreshing.
2. **Contention charges nothing, via `credential_busy`.** Lease acquisition happens after the phase claim and before any container exists. (Claim-time lease filtering would require a cross-context join into assets state, so it is at most an advisory projection — correctness never depends on it.) Losing acquisition yields the typed outcome `credential_busy`: a short not-before requeue on the heartbeat scale that charges neither chargeable failures nor execution usage — a run waiting for a busy credential costs nothing.
3. **Attempt manifest.** The trusted attempt manifest records credential id, the materialized secret version, custody mode, and the auth mount path — so reconciliation and adoption know a materialized credential is in play without resolving anything through agent-writable state.
4. **Directory mount, host-backed, cleanup fenced.** caesar materializes `auth.json` into an attempt-private, host-backed *directory* bound into the container home, outside the workspace bind — a directory, not a single-file bind, so the CLI is free to use whatever write strategy it likes (including sibling temp or lock files), and the contents survive container teardown to be readable afterwards (the container home itself is ephemeral tmpfs). The auth directory sits **outside the attempt directory's blanket teardown** and is removable only under the current lease epoch: a worker whose lease was taken over skips auth-directory cleanup entirely and relinquishes it to reconciliation. The database epoch fence alone is not enough — a paused worker resuming after takeover would otherwise run its deferred recursive teardown and destroy the recovery file before the reconciler reads it.
5. **Guarded read-back.** On *every* exit path — success, failure, kill, reconciliation, adoption — sync-back reads a bounded regular file and requires valid JSON; missing, truncated, or malformed content preserves the stored credential untouched.
6. **CAS update with idempotent receipt.** Credentials gain a monotonic `secret_version`; the sync-back update is compare-and-swap against **both** the version the attempt materialized and the current lease epoch (point 1), committed atomically with an idempotent sync receipt keyed by attempt id and the audit row. The receipt makes the commit-then-crash retry recognizable as *already applied* — it can never be mistaken for, or clobber, an operator rotation. If the operator rotated the credential mid-attempt, the CAS loses and the attempt's sync-back is discarded — a stale run never overwrites a fresh operator-supplied credential.
7. **Accepted loss window.** The Codex CLI persists refreshed tokens by truncating and rewriting `auth.json` in place — not atomically — and the provider may have already invalidated the old refresh token by the time the new one is being written. A kill landing inside that write (host crash, deadline kill, reconciliation kill) can therefore destroy the only copy of a live token: read-back correctly preserves the stored credential, but that credential may already be dead. **Zero-loss rotation is explicitly not guaranteed** — it would require provider-side refresh brokerage or CLI cooperation, both out of scope. The outcome of this narrow window is `auth_expired` plus the operator re-auth loop (§4, §5), which is exactly the failure mode this spec already treats as routine.

8. **Terminalization never skips sync-back.** Run terminalization — including the wall-deadline backstop that fires when caesar restarts after an outage — must not supersede a credential-bearing live phase past its reconciliation. Such phases complete the full sequence first: kill the runtime, guarded sync-back with durable receipt, lease release. The credential-cleanup obligation is **claimable independently of the phase's terminal status**, so a phase superseded by deadline sweep never strands a lease forever or leaves a refreshed `auth.json` alive until the orphan sweeper silently deletes it. (Without this, the implemented janitor order — deadline sweep before lease sweep — creates exactly that trap.)

**Import is exclusive custody transfer.** The single-flight lease serializes *caesar's* runs — it cannot fence writers caesar can't see. So: the recommended provisioning path is a dedicated `codex login --device-auth` for caesar, making caesar's copy the only live copy. Importing a laptop's `auth.json` transfers custody — the source copy must stop being used, and the credentials UI says so at import time. caesar refuses a second *active* `agent_auth_file` credential with the same refresh-token fingerprint (two rows sharing one refresh token would hold independent leases against the same underlying credential). An external live copy remains undetectable by construction; it voids the single-flight guarantee, and the Codex CLI treats refresh-token reuse as terminal — which surfaces in caesar as `auth_expired`, the routine recovery loop.

`subscription_token` needs none of this — it is static and shareable across parallel runs.

## 3. Runtime delivery

**Custody mode joins the harness driver contract**: `materialized` (the real credential enters the agent container) or `brokered` (Plan 06's gateway header-injection; the container holds only an attempt-scoped broker token). Claude Code and Codex drivers both pin **`materialized`** — an explicit, user-ruled relaxation of the V1 spec §3 "no reusable secret in the agent container" property for *provider* credentials in personal mode. `brokered` remains implemented and is the mode API-key-based drivers use. **Forge credentials are untouched**: they never enter agent containers today and still don't (staging contract unchanged).

Per-harness mechanics:

- **Claude Code**: `CLAUDE_CODE_OAUTH_TOKEN` set in the agent container env. Accepted trade-off, recorded: the value is visible to `docker inspect` on the host — which in personal mode is the operator and no one else.
- **Codex**: `auth.json` materialized via the host-backed auth directory mount (§2 protocol), inside the container home but **outside the workspace bind**. Read back under the §2 guarded sync-back on every exit path.

**Immutable credential binding.** The phase's credential binding — id, kind, custody mode, expected `secret_version` — is pinned at phase materialization and travels intact through `ExecutionRequest` → `RunSpec` → attempt manifest; the runner materializes exactly that binding. It must **not** re-resolve the credential through the mutable harness row at execution time (the implemented runner does — `ExecutionRequest` carries only the harness id, and the current credential is read off the harness row when the attempt starts). Without the binding, an admin swapping a harness's credential between materialization and execution would lease credential A and hand the container credential B, bypassing B's single-flight entirely.

**Secret-exposure boundary, stated honestly.** Placing credentials outside the workspace prevents *accidental* capture by the diff/extract pipeline and failure snapshots — it is not a structural guarantee, because the agent can read its own credential and could copy it into the workspace or print it to logs. Two consequences, both binding on Plan 07: (1) the residual risk — agent-held code deliberately exfiltrating a credential the agent legitimately holds — is **explicitly accepted** as part of the materialized-custody ruling (§7.4); (2) accidental persistence is still mitigated mechanically by an exact-value redaction scan with two precision rules. *What is scanned for:* a pinned per-kind sensitive-field list — the Claude token value, and for `auth.json` its token fields (id/access/refresh tokens, API key), initial *and* refreshed — **not** every string leaf, because `auth.json` also holds benign short values (`auth_mode: "chatgpt"`, timestamps) whose exact-match would fail legitimate patches; a minimum-secret-length floor backstops the list. *Where:* workspace-derived artifacts are scanned before persistence, against the **canonical decoded bytes** — Plan 06 stores patch bytes base64-encoded in artifact payloads, so scanning serialized payloads would never find a raw token; the scan runs on the decoded patch before artifact insertion. A hit in a patch or declared artifact fails closed (typed outcome, artifact not persisted). Logs stream to a **quarantined** location, are rescanned after guarded read-back and reconciliation (a mid-run-refreshed token is unknown to caesar until read-back, so scanning only at write time would miss it), and only the redacted copy is atomically published as the durable log artifact.

**Egress gateway: materialized custody pairs with the existing open-CONNECT mode.** The gateway keeps its role — CONNECT proxy, per-harness FQDN allowlist, default-deny, denials logged as `phase.egress_denied` — but for materialized drivers it runs in the **open-CONNECT configuration Plan 06 already built**: no gateway-side provider endpoint or credential, empty broker-token digest, allowlist as the sole barrier. This pairing is load-bearing: the implemented gateway rejects any CONNECT without a valid `Proxy-Authorization` broker token *unless* it runs tokenless, and unmodified CLI HTTP stacks speak plain `HTTPS_PROXY` CONNECT without proxy credentials. The Plan 06 invariant survives intact — an open gateway holds nothing worth stealing (`NewGateway` refuses tokenless-with-credential); materialized custody is exactly the case where the gateway holds no provider credential. Brokered drivers keep the token-authenticated gateway unchanged. Allowlist requirements:

- Codex's token-refresh endpoints (`auth.openai.com` family) **must** be allowlisted, or the CLI cannot refresh mid-run and long runs die opaquely.
- CLI telemetry endpoints (Statsig, Sentry for Claude Code) default **denied**. The CLIs tolerate this; denial events make any future CLI-update breakage diagnosable.
- Exact FQDN lists per harness are pinned in Plan 07 (they drift with CLI releases; the plan records the verified-current set and the denial events catch drift).

## 4. Cap-hit and auth-death handling

Both are typed outcomes. `auth_expired` rides the existing Plan 05 machinery unchanged; `rate_limited` does **not** — the implemented spine has no way to express "retry, but not before time T" (retry rows are immediately claimable, and every transient failure burns the attempt budget), so delayed resume is specified here as an explicit, small spine extension. No new phase *statuses* and no transition-table changes, but a schema migration and claim-predicate change, owned by Plan 07:

- **`rate_limited`** (subscription cap window exhausted — e.g. Claude's rolling 5-hour window, ChatGPT message limits): the attempt requeues with a durable **not-before** eligibility time — the provider-surfaced window reset when available, otherwise a conservative backoff. The delayed-retry contract:
  1. `phase_runs` gains a nullable, indexed `not_before` column; the claim CTE adds `(not_before IS NULL OR not_before <= now())`, evaluated against the database clock like the existing deadline predicates.
  2. The typed `Outcome` carries an optional structured retry-at time (not a parsed message string).
  3. **Cap waits are exempt from ordinary attempt exhaustion** — several cap windows inside one long run must not fail it as `attempts_exhausted` while its wall deadline is unexpired. The mechanism is pinned here, because the attempt number cannot do double duty: `attempt` stays an always-increasing execution ordinal (the `(run, node, attempt)` identity and its unique index are untouched), and `phase_runs` gains a **chargeable-failure counter** carried forward on retry insertion. Ordinary transient failures increment it; `rate_limited` does not. Retry-insertion guards and exhaustion decisions read the counter; the claim predicate drops its `attempt <= max_attempts` guard in favor of it. Consequence to document in events/API: `attempt` may legitimately exceed `max_attempts` on cap-heavy runs — `max_attempts` bounds *charged failures*, not executions.

  4. **Fallback scheduling is pinned.** Provider-surfaced reset times are normalized against the database clock; absent, malformed, or already-past values fall back to a per-provider default backoff with a hard minimum retry floor — a reset-less provider must never degenerate into a rapid retry loop minting unbounded attempt rows. If eligibility would land beyond the run's wall deadline, the run terminalizes immediately with its typed outcome instead of parking a row that can never legally run.

  The run stays alive and resumes unattended. Caps are a fact of life on subscriptions, so this is a first-class waiting condition, not an error.
- **`auth_expired`** (token dead or revoked): the run **fails fast with that typed outcome, naming the credential**. Deliberately *not* a parked awaiting-credential state: the operator is around by posture (preamble, §1), re-auth plus rerun is a 30-second loop, and park-and-auto-resume machinery is v1 bureaucracy. Parking can be added later without schema churn if practice demands it.

The asymmetry is deliberate: **caps heal themselves, so runs wait; dead auth needs human hands, so runs fail fast.** Mapping each CLI's exit codes and output to these outcomes is per-harness driver logic — the Plan 07 "exit→outcome mapping" work, with these two rows now specified.

**Per-provider concurrency note:** the `agent_auth_file` single-flight rule (§2) already serializes Codex. No additional per-provider concurrency limiter is specified for v1; if parallel Claude runs burn the cap window too fast in practice, a limiter is a policy knob to add later, not a spine change.

## 5. Operator loop

- **Credentials in**: the existing admin credentials API grows the two new kinds — paste the Claude token or the `auth.json` contents exactly like a `model_key` today (encrypted at rest, use-audited). One sizing change: the flat 4 KiB secret cap fits model keys but not a multi-token JSON file, so `agent_auth_file` gets a per-kind bound (64 KiB) with matching request-body limits and a maximum-size test. **No embedded OAuth flows in caesar** — minting happens on the operator's laptop or via device-auth on the box.
- **Knowing when they die**, two cheap signals:
  1. Any run failing `auth_expired` names the credential in its typed outcome — visible in run detail and the event stream.
  2. The credentials view shows passive freshness: last successful use, last `auth_expired`, and for `subscription_token` the recorded provided-at date (a ~1-year token's age is visible before it dies mid-run).
- **No proactive token-probing cron**: the CLIs are the source of truth for whether auth works, and a probe would spend cap window to ask.

## 6. Verification & plan mapping

**Testing boundaries (honest about what CI can prove):**

- Driver-level unit tests run against recorded CLI behavior (exit codes, output shapes) — no live subscription calls in CI, ever.
- The `runnerintegration` lane proves materialization mechanics with fakes: credential lands in the host-backed auth mount outside the workspace bind; the redaction scan catches a planted secret in a patch (fail-closed) and in the log stream (redacted); sync-back captures a mutated `auth.json`; gateway open-CONNECT mode carries CLI-shaped TLS CONNECT traffic (including the Codex refresh FQDNs) with no proxy credential.
- The delayed-retry contract gets spine-level tests: deadline-boundary (not-before beyond wall deadline terminalizes), restart survival (not-before holds across orchestrator restart), repeated cap windows in one run never yield `attempts_exhausted`, a not-yet-eligible row is invisible to a concurrent claim, and scheduling-fallback cases (absent, malformed, and already-past reset values hold the retry floor with bounded attempt-row creation).
- The credential-lease protocol gets a crash-injection matrix: crash before refresh, during file replacement, after refresh but before store commit, and after commit but before lease release. Every case must end with a releasable lease and a store that is either usable or honestly `auth_expired` (the §2.7 accepted loss window — the mid-replacement case may legitimately land there); the post-commit case must prove the receipt makes the retry idempotent. Race tests: a competing claimant during the previous owner's reconciliation must not acquire until sync-back concludes; a worker paused immediately before sync-back while reconciliation takes over must be unable to commit its stale snapshot (epoch fence); a worker paused before its deferred teardown, resuming after takeover, must not delete the auth directory (cleanup fence); a harness credential swapped between phase materialization and execution still runs under the originally bound credential (binding race). Lifecycle test: caesar restarts *after* a credential-bearing run's wall deadline passed mid-outage — the container is killed, sync-back lands with its receipt, the lease releases, and only then does the run terminalize. Contention test: a run queued behind a held `agent_auth_file` lease consumes zero execution budget and zero charged failures while waiting.
- Redaction precision tests: a legitimate patch containing the literal `chatgpt` persists fine; a token refreshed mid-run and printed to logs just before a worker crash is still redacted before the log artifact is published; the patch scan proves itself against the real collected artifact representation (base64-decoded canonical bytes), not a synthetic plain-text patch.
- One **manual smoke checklist** in Plan 07, run once by the operator on real subscriptions, validates the two live paths end to end. That is the boundary between what CI can prove and what only a real token can.

**Plan mapping:**

- Everything above lands in **Plan 07** (harness drivers, subscription-first). Sequencing: PR #6 goes green and merges → this spec is committed → Plan 07 is authored from it.
- **Plan 09 scope note**: token/cost metering is demoted for subscription runs (flat-rate; nothing meaningful to meter). Request/byte/denial counts from Plan 06 stay. Cap awareness (§4) replaces cost accounting as the interesting signal.

## 7. Decision log (user rulings, 2026-08-05)

1. Personal single-user platform; subscription auth first-class from day one; multi-tenant out of scope.
2. Operator is the credential custodian and the human refresh loop; caesar surfaces auth death, never runs OAuth flows itself.
3. Cap-hit = waiting state with auto-resume, bounded by the run deadline. Auth-death = fail fast with typed outcome.
4. **Custody = `materialized` for both harnesses** (user ruling over the assistant's keep-Claude-brokered lean; uniformity and laptop-equivalent trust posture on a personal box). `brokered` stays implemented for API-key kinds; decision is a per-harness flag, reversible.
5. Codex `agent_auth_file` is single-flight; Claude `subscription_token` shareable across parallel runs.
